# TextDecoder/WHATWG vs Python's `codecs` + `unicodedata`

chardet is written against CPython: it decodes bytes with the `codecs` module
and classifies characters with `unicodedata`. The port runs in the browser and
in Node, where the equivalents are `TextDecoder` (the WHATWG Encoding Standard)
and Unicode property escapes like `\p{L}` (the JS engine's ICU database). Those
two worlds disagree, and almost every "why is there a generated table here?" in
this codebase traces back to one of the disagreements below.

This doc is the conceptual home for that fault line: the gaps, the bridge the
port builds for each, and why a single bridge can't span the whole thing.
Per-file mechanics live in [architecture.md](architecture.md) and
[port-notes.md](port-notes.md); this is the map that ties them together.

## The gaps

**1. Coverage — `TextDecoder` lacks decoders chardet needs.** Several encodings
in chardet's registry have no WHATWG decoder at all: the EBCDIC pages (cp037,
cp500, cp1026, …), hp-roman8, koi8-t, cp1006, and more. There is no runtime way
to even obtain the decoded character.

**2. Strictness — WHATWG decoders accept bytes Python rejects.** The WHATWG
spec is built to *never* fail on a single-byte decode, so it gap-fills
positions CPython's strict codecs leave undefined:

- the windows-125x pages leave a few C1 slots undefined (0x81, 0x8D, 0x8F,
  0x90, 0x9D under cp1252); `TextDecoder('windows-1252')` maps them anyway;
- `TextDecoder('ascii')` is a WHATWG *alias for windows-1252*, so it decodes
  every high byte instead of rejecting `>= 0x80`.

Python's `bytes.decode(..., 'strict')` raises on all of these. Detection leans
on that rejection to eliminate candidates, so the port has to reproduce it.

**3. Codec collapse — WHATWG maps a subset and its superset onto one decoder.**
Its `shift_jis` *is* cp932, its `euc-kr` *is* cp949. CPython keeps them
distinct: plain `shift_jis` raises on a CP932-only byte that `cp932` decodes.

**4. Category drift — ICU's UCD is not CPython's UCD.** Even where a character
decodes, its Unicode general category comes from the JS engine's bundled ICU,
which can trail CPython's `unicodedata` by a Unicode version or two. A
code point assigned in the newer version reads as `Cn` (unassigned) under the
older one, so category-based logic can silently diverge.

## The bridges

The port bridges each gap by extracting the authoritative answer from Python at
build time (during `update-chardet`) and shipping it as data, or by
reimplementing the exact behavior, or — where neither is worth it — by
documenting the divergence and pinning it with a test.

The bridges below are ordered by strength of solution, not by gap number —
cleanest data extraction first, then reimplementation, and the last two are
deliberately unsolved (a documented divergence and an accepted caveat).

### Undefined single-byte positions (gap 2) → `sbcs-undefined-bytes.ts` + validity predicates

[`scripts/generate-sbcs-undefined-bytes.js`](../scripts/generate-sbcs-undefined-bytes.js)
records, per single-byte encoding, the byte values Python's strict codec
rejects. The validity stage consults it *before* `TextDecoder`, so windows-125x
(and other SBCS with WHATWG labels) match CPython instead of WHATWG's
pass-through. The two predicates that must reproduce Python's judgment live in
[`pipeline/validity.ts`](../src/pipeline/validity.ts): `decodesUnderValidity`
(tolerant, the `filter_by_validity` question) and
`decodesCompletelyUnderValidity` (strict/whole-input, for the decode-safety
flip and the past-cap hold). Both special-case `ascii` as strictly 7-bit,
closing the ascii≡windows-1252 alias.

### Missing decoders + category drift (gaps 1 & 4) → `_byte-decode-tables.ts`

The deepest bridge, because it answers *both* "what does this byte decode to?"
(for encodings TextDecoder lacks) and "what is that character's category?" (at
CPython's UCD version, immune to ICU drift). Generated by
[`scripts/generate-byte-tables.js`](../scripts/generate-byte-tables.js) over
every encoding in the registry.

**Format**, per encoding:

- `cats` — a 256-char string; `charCodeAt(b)` is byte `b`'s Unicode general
  category, as an index into `_INT_TO_CATEGORY`. All 256 bytes, because the
  letter-case derivation (below) classifies neighbour bytes of any value.
- `cps` — a 128-char string covering only the **high** bytes; `charCodeAt(b -
  0x80)` is the decoded code point of byte `b` (`0x80`–`0xFF`), or the sentinel
  `0xFFFF` when the byte does not decode, or `0xFFFE` when it decodes to zero or
  more than one character (a stateful codec's shift byte). Both sentinels are
  Unicode noncharacters, so a real single-byte decode (always a BMP scalar)
  can't collide with them, and `differingHighBytes` compares the values for
  equality. Low bytes are omitted: no consumer reads a code point below `0x80`.

**Three consumers** in [`pipeline/confusion.ts`](../src/pipeline/confusion.ts):

- `differingHighBytes(a, b)` — the byte values `>= 0x80` where two encodings
  decode to different text, read from `cps`. Arbitrates pairs the confusion
  maps don't cover (the era prior).
- `_pairCategories(a, b, diffBytes)` — each distinguishing byte's category
  under both encodings, read from `cats`. (Feeds the niche-Latin demotion's
  arbitration.)
- `_letterCaseTable(enc)` — the 0/1/2 letter-kind chardet's `_letter_case_table`
  computes (0 non-letter, 1 uppercase letter, 2 other letter / combining mark).
  This verdict is a **pure function of the general category**, so the port
  *derives* it from `cats` rather than storing a second table. The generator
  asserts the derivation equals chardet's own table byte-for-byte before
  emitting; if a future chardet changes the rule, the assert fails loudly at
  pin time.

### EBCDIC markup declarations (gap 1) → the cp037 table in `markup.ts`

Charset declarations inside EBCDIC-encoded markup can't be read with any WHATWG
decoder. [`pipeline/markup.ts`](../src/pipeline/markup.ts) bakes a cp037 byte→
character table (from Python's codec) to decode the head and find the
declaration; the declared MAINFRAME-era name's own decode check reduces, for a
single-byte encoding, to "contains no undefined byte" — answered from
`sbcs-undefined-bytes.ts`.

### UTF-7 (gap 1) → a hand-rolled decoder

`TextDecoder` has no UTF-7. `utf7DecodesWithoutError` in
[`pipeline/to-utf8.ts`](../src/pipeline/to-utf8.ts) reimplements CPython's
`utf_7` incremental decoder's error behavior, pinned against CPython by the
oracle cases in `tests/escape.test.ts`.

### Codec collapse (gap 3) → documented divergence, not bridged

This is the one gap the port *cannot* close with data, because the fix would
mean shipping its own CJK decoders. Under WHATWG, `shift_jis` decodes a
CP932-only byte that CPython's `shift_jis` rejects, so chardet's markup
decode-safety promotion (declared-Shift_JIS → CP932 when the plain codec can't
decode) can never trigger. The port leaves it unported, documents it under
"Markup superset decode-safety promotion" in [port-notes.md](port-notes.md),
and pins its own behavior with a divergence test. Three corpus files surface it
in `tests/compare-detect` (two cp932, one cp949); all pass the accuracy gate
via the `prefer_superset` remap or byte-equivalence.

### Arbitrary-text category scoring (gap 4) → `\p{...}` with a documented caveat

[`pipeline/utf1632.ts`](../src/pipeline/utf1632.ts) scores UTF-16/32 text
quality by classifying arbitrary decoded characters (`\p{L}`, `\p{M}`, `\p{Zs}`,
`\p{C}`). Unlike the single-byte tables, this runs over unbounded text, so
tabling it would mean shipping a general UCD snapshot. The drift rarely changes
a ranking, so the port accepts `\p{...}` here and documents the caveat in
architecture.md §e.

## Toward a unified shim (a direction, not done here)

Every bridge above is a point-solution to the same root need: *faithfully
answer "decode these bytes as CPython would" and "what is this code point's
category at CPython's UCD version."* The natural general solution is a single
build-time-extracted **"codec + unicodedata" data layer** that every site
queries, instead of each reaching for `TextDecoder` / `\p{}` / its own table.

The single-byte, build-time-known slice is most of the way there already:
`_byte-decode-tables.ts` unifies *decode-single-byte* + *category* +
*letter-kind* behind one artifact. The next consolidations would subsume more:

- fold `sbcs-undefined-bytes.ts` into it — a byte is "undefined" iff its `cps`
  entry is the sentinel, so the validity SBCS check becomes the same lookup;
- route the cp037 EBCDIC markup table through it too.

That would collapse three single-byte tables into one lookup API. It is a
worthwhile future cleanup, deliberately **not** bundled into a chardet-update
commit: it is an orthogonal internal refactor across `validity.ts` and
`markup.ts` with real regression surface and no behavior change, and it reviews
far better as its own focused change.

Two corners resist the general solution for structural reasons, not for lack of
effort:

1. **Multibyte decoding can't be tabled.** You can't enumerate CJK sequence
   space, so `TextDecoder` stays for the multi-byte encodings — and that is
   exactly where the codec-collapse divergence (gap 3) lives. Only shipping
   first-party CJK decoders would close it, which is enormous and not
   worthwhile for the handful of corpus files affected.
2. **Category scoring over arbitrary text (utf1632) needs general UCD
   coverage.** A faithful snapshot there is large, for a heuristic where the
   drift seldom changes the answer — so `\p{...}` with a documented caveat is a
   deliberate cost trade, not something a single-byte table can absorb.

So the general solution genuinely exists for the single-byte / build-time-known
corner, and consolidating toward it is real future work; the multibyte-decode
and arbitrary-text-category corners stay point-solutions on purpose.
